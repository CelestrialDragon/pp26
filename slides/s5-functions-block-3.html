Block 3 — Continuations: what does the computation do next?

Block 1 handed over one step of a traversal, block 2 a computation not yet run. This block hands over the rest of a computation. It is the ground for session 6: a promise is a value that is not there yet, together with what to do when it arrives, and "what to do when it arrives" is what we write today.

Block 3: the four parts

In block 2 we called a function to get a value. In this block we call a function to give it a value: it does what is still to do with it.

PART 1

The rest, as data

What did the stack of count hold?

Session 4: count, twice

def count(m):
    if m[0] == "Note": return 1
    return count(m[1]) + count(m[2])

A recursion. On a melody 100 000 notes deep it fails: the machine's stack is full.

def count(m):
    n, stack = 0, [m]
    while stack:
        m = stack.pop()
        if m[0] == "Note": n += 1
        else: stack += [m[2], m[1]]
    return n

A loop and a stack of our own. It counts the 100 001 notes.

We count the notes of ((C D) (E F)), and C has just been counted. What does the stack hold? What do the frames of the recursion hold?

Both are on session 4's slide "Can a loop replace every recursion?", and on slide 2 of block 1. Say that the loop is a complete solution: nothing is wrong with it, and the block does not replace it. ((C D) (E F)) is the melody Seq (Seq (C, D), Seq (E, F)); a note is written by its name. Let the room answer the two questions, the stack first; the next slide shows both.

Both hold the subtrees still to visit. A frame also holds what to do with the result, written _: an addition. The loop needs no such thing: it has n.

What is still to do when a call returns is the rest of the computation. The machine keeps it in a frame. The loop keeps it in a stack, as data.
The stack was printed by demos/count_k.ml: n = 1, stack = [D; (E F)]. The frames are session 4's: a frame holds the work still to do after the call. _ is the place of the result that the frame waits for, as on session 4's slide on the tail call ("no pending 3 + _"). The stack of the loop can hold subtrees only because the work still to do has one shape here, count this and add; with two shapes each entry would need a tag. A function has no such limit: this is where part 2 goes.
PART 2

The rest, as a function

Can we write what is still to do as a function?

sum, and sum with k

let rec sum l = match l with
  | [] -> 0
  | x :: rest -> x + sum rest

In x + sum rest, what is still to do when sum rest returns?

We add x to its result, and we return the sum to our caller.

let rec sum_k l k = match l with
  | [] -> k 0
  | x :: rest ->
      sum_k rest (fun v -> k (x + v))

k is what our caller does with the sum. sum_k does not return the sum: it calls k with it.

sum_k [3; 1; 4] (fun v -> v) = 8
A function that receives a result and does what is still to do with it is a continuation. We name it k.
The smallest case, on a list. Read the last line of sum_k aloud: the sum of the rest is called v; what is still to do with v is to add x and to give the sum to k. That is the answer given on the left, written as a function. The first continuation, fun v -> v, returns what it receives; with fun v -> Printf.printf "the sum is %d\n" v the program prints "the sum is 8". Recorded from demos/sum_k.ml. The next slide runs sum_k [3; 1; 4] step by step.

sum_k [3; 1; 4], step by step

Step or Run; nine steps, in two phases. The line of code is the call that the program is making. First phase: for every element one continuation is built, which holds the element and the continuation built before it; the arrow is that k. Nothing is added. Second phase: at the empty list the last continuation built is called with 0, it adds 4 and calls the one below, and so on down to k0. It is the order of the recursion: sum adds 4 first as well. demos/sum_k.ml prints these nine lines. Model: last year's trace of factorial in two phases. The drawing is a stack on purpose; the next slide says why.

A frame and a continuation

a frame of sumfun v -> k (x + v)
what to do with the resultthe return address: x + _its code: k (x + v)
what it needs for thatthe local variable x, savedx, in its environment
what comes afterthe frame belowk, in its environment
A frame is used once, by the machine. A continuation is a value: we decide what becomes of it.

In sum_k every call is a tail call: no frame waits, and what is still to do is on the heap, in the closures. This way of writing is called continuation-passing style.

a list of 1 000 000 numbers, a stack of 10 000 words
sum:   Stack_overflow
sum_k: 499999500000
This slide pays the promise of block 1's slide 2: "for answers 2 and 3 we passed a function as a value; at the end of session 5 we do the same for answer 1, with continuations". Answer 1 was the frame. A continuation is a closure, block 1's part 1: code and an environment. The rewriting from sum to sum_k follows a fixed rule, and a compiler can apply it: session 6, async and await. The output is demos/sum_k.ml run with OCAMLRUNPARAM=l=10000; with OCaml's own stack, of 128 million words, sum does not fail on this list. The continuations are not free: one closure on the heap for every element, where sum had one frame on the stack; the difference is where, and that a closure is a value.

count, with k

type melody =
  | Note of string
  | Seq of melody * melody

let rec count m = match m with
  | Note _ -> 1
  | Seq (a, b) -> count a + count b

a melody 1 000 001 notes deep: 1000001

While count_k a runs, what does its continuation hold?

It holds b, the right subtree, and k, what was still to do before: the stack of part 1, written as a function.
The melody has the two constructors that session 4's slides used; lab 3's type has four. count_k is written from count by the rule that gave sum_k from sum: every call receives, as a function, what was written around it. There are two calls, so two continuations, one inside the other. Recorded from demos/count_k.ml, on a melody deep to the left and on one deep to the right. PART 3

Keeping the rest

What can we do with k if we do not call it?

A traversal that hands over its rest

let rec iter_k f m k = match m with
  | Note p -> f p k
  | Seq (a, b) -> iter_k f a (fun () -> iter_k f b k)

Our function f receives a note, and k: the rest of the traversal.

iter_k
  (fun p k -> print_string p; k ())
  m (fun () -> ())
CDEF
iter_k
  (fun p k -> print_string p)
  m (fun () -> ())
C

On the right f loses k. What if it returns it?

m is ((C D) (E F)). iter is block 1's internal iteration, where the collection called our function on every element and our function could not stop it. Here our function is given the rest of the traversal. On the left it calls it, and the traversal goes on. On the right it does not, and the traversal has stopped at the first note: nobody holds k any more. Ask for each output before showing it. Recorded from demos/leaves.ml. The last argument of iter_k is what to do after the last note.

A traversal stopped, and resumed

let to_seq m = fun () -> iter_k (fun x k -> Cons (x, k)) m (fun () -> Nil)
Our function returns the note and k, in a Cons; after the last note the answer is Nil. Step or Run; ten steps. The hatched box is block 2's drawing of a computation not yet run. When f returns Cons (C, k), every call of iter_k returns: no call of iter_k is waiting, and what is left of the traversal is the value k, which we hold. Between two steps we can do anything else, for as long as we want. Recorded from demos/leaves.ml: stopped at C, resumed, stopped at D.

In block 2 the rest of a list was its tail. The rest of a tree is a stack of subtrees, and nobody has written that stack.

Two ways out

What is an exception?

The first newline, with k and h

let rec newline_k l i k h = match l with

let ask l =

We pass two continuations: k says what to do with the result, h what to do when there is none.
The text is block 1's, hi, a newline, yo. newline_k gives the position of the first newline to k; at the end of the list it has no position to give, and calls h. The same program in direct style. k is not written either: it is the frame that waits for the result of newline l 0, and h is the handler installed by try. raise leaves every frame between the two at once, as calling h did. This is a model of what an exception does, and it is exact; OCaml implements it with a stack of handlers, not with a closure. Recorded from demos/newline_kh.ml. In session 6, then takes what to do with the value and what to do with the failure; a rejected promise calls the second.

A pattern with *: succ and fail

let lit x s succ fail =
  match s () with
  | Cons (y, rest) when x = y ->
      succ rest fail
  | _ -> fail ()

lit x matches one character x. succ receives the rest of the sequence, and fail.

let rec star x s succ fail =
  match s () with
  | Cons (y, rest) when x = y ->
      star x rest succ
        (fun () -> succ s fail)
  | _ -> succ s fail

star x matches as many x as possible. If what follows fails, it gives one back.

The continuation of success receives the continuation of failure. When what follows does not work out, it calls it, and the search goes back to the last choice.

The match is at the start: aaabXYZ gives true too. For the whole sequence, succ would also ask for Nil.

Not presented. The two continuations of part 4 are named succ and fail, as in the lab. In part 4 h was given once, at the start. Here star makes a new fail at every character that it takes: fun () -> succ s fail ends the star at s, and goes on with the rest of the pattern from there.
